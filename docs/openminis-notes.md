## 一、架构规范（agent loop / 工具契约 / 会话持久化）

**可借鉴的点**
- 循环每轮调 API 前先对历史做"消毒"：给缺失配对的工具调用结果补占位，防止 API 拒绝悬空 tool_calls。云开当前信任自己写的历史构造，但「取消/崩溃后重进会话」场景下确实可能产生孤儿 assistant tool_calls（云开净空语义不落库中间轮，暂无此风险，M2 若做断点续跑就要补）。
- 上下文压力检查分"卸载/压缩/耗尽"三档，旧的大工具输出卸载到磁盘原地留存根（提示模型可用工具取回）。云开 M2 的 B4 记忆库/预算截断可直接采用这套分档思路。
- 错误先分类再决定重试：取消、认证/配额类绝不重试；网络/解码/未知类才做有限退避（1s/2s/4s）重试；上下文超限单独走"输入减半重试"。云开现在 LLM 错误直接抛给 UI toast，M2 可按此分类。
- 工具结果三态（成功/失败/**超时**）显式区分，超时单独成态。
- 中断恢复按"尾部形状"判定：会话最后一条消息分类成几种可恢复中断形状，只对确定中断给"继续"入口；刻意不判断"是否还在等待"避免误报。

**与云开现状的差异**
- OpenMinis 循环上限 200 轮、多 provider 翻译层、PRoot 沙箱（云开 M1 是 10 步、单 OpenAI 兼容协议、无沙箱——云开定位轻量桌面 agent，不需要那么重）。
- OpenMinis 用户消息先落库再发请求（崩溃不丢输入）；云开是净空语义（回答成功才落库），两者哲学不同，云开取舍简单但崩溃丢问句。

**是否纳入 M2 backlog**：错误分类重试（值得）；工具结果预算分档截断（已在云开 M2 待办，思路印证）；尾部形状中断恢复（B 系列再做，暂缓）。

## 二、技能系统

**可借鉴的点**
- 渐进式披露：system prompt 只注入「名称+一句话简介+读取路径」的技能清单（限量+优先级+描述截断），说明书全文由模型需要时自己读。技能数量增长时上下文成本近似常数。
- 技能有元数据（来源、版本、启用状态、使用计数）与磁盘目录双向同步；模型改动 SKILL.md 自动触发重扫。
- 注入防御现状：只有 XML 转义+长度截断+坏技能降级，没有专门 prompt injection 检测——说明业界同量级产品也只做到这一步，云开 M2 待办的"转义/截断/过滤"是同等水位。

**与云开现状的差异**
- 云开是「清单注入 + use_skill 工具全文回传」，说明书全文作为工具结果进上下文，每次使用付全文成本；OpenMinis 把读取动作交给模型的 file_read。云开技能数量少（M1 内置 1 个），全文回传更简单可控，暂不改。
- OpenMinis 技能是磁盘目录；云开是 Room 表行（粘贴导入为主）。各 fit 各的场景。

**是否纳入 M2 backlog**：技能描述长度截断（建议纳入，与 prompt injection 防御同批）；使用计数/披露优先级（不纳入，自用无此需求）。

## 三、会话 UI 与流式

**可借鉴的点**
- 流式状态模型：高频变化字段（增量文本）从消息对象剥离到按 id 索引的旁路状态图，token 级更新只重组单个列表项；流结束一次性"排干"回正式消息。云开 M2 的 B1 SSE 流式若直接把增量写进消息列表会整屏重组，此模型是现成答案。
- 自适应节流：按已累积文本长度分档（短回复 150ms → 长文 2s），渲染端二次节流+合并采样。
- 流式消息永不折叠、超长已冻结消息才折叠——防阈值穿越闪烁。

**与云开现状的差异**
- 云开 M1 非流式（stream=false 忠实移植），B1 才引入 SSE；B1 实施时直接采用"旁路状态+节流"设计。
- OpenMinis 列表内不渲染长 HTML（文件 chip + 独立预览层）；云开 M1 是列表内嵌 420dp WebView 卡。云开页长有限（eli5 页 15-60KB），暂保持移植忠实度；若滚动卡顿复现，按鸿蒙版同款待办（快照缓存或全屏复用单实例）处理。

**是否纳入 M2 backlog**：B1 流式的状态模型与节流方案（纳入，B1 实施前把此节写成设计输入）。

## 四、HTML 输出渲染

**可借鉴的点**
- 加载方式按信任级别分档：无人值守/静态内容禁 JS + 无 base URL 的 data 式加载（origin 落 about:blank 天然无特权）；交互页面才开 JS 并关 file 访问。云开「data:base64 + 禁 JS」与其静态档完全同构，方向互相印证。
- WebView 单例复用：预览层单 holder 跨多个 Compose 目标共享，切换不销毁不重载不丢滚动位；销毁时停加载→置空白→destroy 的顺序。
- 推迟到 attach 且完成正尺寸布局后再加载（防 vh 单位按 0 高度解析白屏）；容器高度变化时向页面派发 window resize（Android WebView 不会自动通知）。
- 列表内嵌 WebView 的教训：能不嵌就不嵌；必须嵌时做内容寻址缓存+字节预算。

**与云开现状的差异**
- 云开画布卡在 LazyColumn 里嵌 WebView（MVP 接受多实例开销，鸿蒙版同样如此且有同款卡顿待办）。Android 侧本轮保持忠实移植，风险清单已记录。

**是否纳入 M2 backlog**：画布卡滚动卡顿的"单实例复用"方案（与鸿蒙 M2 待办同款，双端一起裁决）。

## 五、对云开最有价值的 5 条（按 M2 顺序）

1. **B1 SSE 流式**：采用"旁路状态图 + 自适应节流 + 终值排干"状态模型，避免 token 级整屏重组。
2. **B3 文件读写**：工具结果契约里给"持久产物附内部可寻址 URL"，模型能把产物以链接形式还给用户。
3. **B4 记忆库**：上下文预算做纯函数策略（卸载/压缩/耗尽三档），大工具输出卸载留存根。
4. **错误分类重试**：取消/认证/配额不重试，网络/解码/未知有限退避，全部有总预算封顶。
5. **技能注入防御**：清单与描述转义+截断（与 OpenMinis 同水位），prompt injection 检测业界尚无标准做法，先做基础硬化。
